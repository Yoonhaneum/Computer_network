Task 1 — Link-State Routing

Dijkstra 알고리즘을 구현하여 각 노드에서 다른 노드까지의 최단 경로 비용을 계산하고 forwarding table을 구성하였다. 노드 u에서 계산한 최단 경로 비용은 v=2, w=3, x=1, y=2, z=4였다. forwarding table에서 목적지 w, y, z로 가는 다음 홉은 x로 결정되었다.

이후 u-x 링크가 다운된 상황을 적용하여 forwarding table을 다시 계산하였다. 링크 장애 이후 목적지 x, w, y, z로 가는 다음 홉이 각각 v, w, v, v로 변경되는 것을 확인하였다. 이를 통해 링크 상태가 바뀌면 최단 경로와 forwarding table도 다시 계산되어야 함을 확인하였다.

Task 2 — Traceroute and OSPF

Traceroute를 수행하여 국내외 목적지까지 패킷이 거치는 홉을 관찰하였다. 라우터의 라우팅 테이블을 링크 장애 전후로 비교하고, 장애 이후 경로가 변경되는 것을 확인하였다. 또한 OSPF의 경로 재계산과 수렴 시간을 기록하였다.

이 실험을 통해 라우팅 프로토콜은 최단 경로를 처음 계산하는 것뿐 아니라, 링크 장애가 발생했을 때 새로운 경로를 계산하고 라우팅 테이블을 갱신하는 역할도 수행한다는 점을 확인하였다.

Task 3 — Incremental Reconvergence

400개의 라우터, 1,581개의 링크, 1,000개의 이벤트를 사용하여 기준 구현과 증분 갱신 구현을 비교하였다. 기준 구현은 SPF를 1,001회 실행하는 데 약 1.07초가 걸렸고, 증분 갱신 구현은 SPF를 363회 실행하는 데 약 1.40초가 걸렸다. 증분 갱신 구현은 기준 구현보다 SPF 실행 횟수를 약 64% 줄였으며, 모든 이벤트 처리 후 라우팅 테이블이 정확했다.

그러나 SPF(목적지까지 최소 경로 계산) 실행 횟수가 줄었음에도 전체 실행 시간은 약 0.33초 더 길었다. 이는 SPF 계산 자체를 줄이는 것과 프로그램 전체의 실행 시간을 줄이는 것이 서로 다른 목표임을 보여준다. 증분 갱신에는 변경 영향을 확인하고 갱신할 대상을 판단하는 추가 비용이 발생할 수 있다. 따라서 작은 실험에서 계산 횟수가 줄어드는 것만으로 실행 시간이 개선된다고 단정할 수 없다. 실제 성능을 평가할 때는 SPF 실행 횟수, 테이블의 정확성, 전체 실행 시간을 함께 고려해야 한다.
